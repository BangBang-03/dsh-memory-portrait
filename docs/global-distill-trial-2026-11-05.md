# 二级蒸馏试跑：dsh-memory（2026-11-05）

一次"先验证产物、再建管道"的实操记录。目的不是产出正式全局记忆，而是回答两个问题：

1. 从单个项目的记忆里，能不能蒸馏出**跨项目仍然成立**的原则？
2. 如果能，产出的密度是多少？值不值得建两级管道？

| note | 24 | 低——多为过程记录 |

## 筛选标准

一条候选原则必须同时满足三条，否则淘汰：

1. **至少 2 个锚点**。只有一条记忆支撑的，可能是偶发偏好，不足以称为原则。
2. **不含项目载体**。不得出现文件名、命令、包名、版本号、路径、项目名。
3. **保留约束强度**。用「必须 / 不要 / 不可」，不写成「倾向于」「建议考虑」——后者无法执行。

## 产物：4 条候选原则

### P1 · 只声明实测过的状态，未验证就明确标 unknown

> 任何对外声明（兼容性、支持范围、性能数字）都必须有实测依据；没测过的写 unknown，不靠推断补齐。

锚点：

- 《兼容性声明只标实测过的 DSH 版本，未测写 unknown》
- 《独立审查要重跑代码与数据给自测数字，不复述文档》
- 《一手验证要求》

约束强度：必须。

### P2 · 不可逆操作先备份，且不做自动裁决

> 改动真实数据前先留一份可回滚的快照；合并、归档、删除这类不可逆动作不能由系统自动决定，要逐项人工确认。

锚点：

- 《改动真实记忆库前先做整库快照与台账备份》
- 《矛盾不再自动归档，改为用户逐对确认按时序归档》
- 《归档 / supersedes 而不是删除，推翻要能回滚》

约束强度：必须。

### P3 · 后台任务不阻塞主流程，失败要有冷却

> 自动整理、自动重写这类后台任务一律在轮次之外跑；带失败冷却与并发让步，任何失败都不能影响当前对话。

锚点：

- 《自动整理 / 自动画像不阻塞轮次：失败冷却 + 并发让步》
- 《自动巩固必须挂 turn/end，不能挂 agent/turn-stopping》

约束强度：必须。

### P4 · 对外素材不用真实数据

> 文档、截图、演示一律使用构造数据并标注来源；真实用户数据只在本地出现。

锚点：

- 《不要用真实记忆面板截图（可能泄露用户数据）》
- 《sessionLogAppend 落盘前必须先脱敏》

约束强度：必须。

## 淘汰分析：为什么 118 条不上行

| 淘汰原因 | 占比估计 | 典型例子 |
| --- | --- | --- |
| 项目载体太重（命令、文件名、版本号） | 最多 | 「publish.yml 自动生成 Release 标题」「npm publish 带 --ignore-scripts」 |
| 一次性决策，已被后续决策取代 | 多 | 「lab 分支与 lab-latest 均已删除」 |
| 只有单锚点，可能只是偶发偏好 | 少 | 「一次提交只做一件事」（本项目只出现过一次） |
| 属于常识，不值得占全局预算 | 少 | 「写测试」「跑全量」 |

最有价值的发现：**convention 类几乎全部不可上行**。21 条里有 18 条是「本项目的发布流程 / 文档同步规则」，写得越具体，越不可能跨项目成立。

真正的通用原则集中在 `feedback`（纠正类）与少数 `decision`（取舍类）。前者记录「用户不接受什么」，后者记录「为什么放弃另一条路」——这两类天然是行为层面的。

## 结论

**合格率约 3%（4 / 122）。**

按 6 个项目估算，候选原则总量约 15–20 条；共振后能留下 3–6 条全局记忆。

这个密度符合「全局层应当是高层信噪比层」的定位——少而硬。但暴露了一个设计问题：

### ≥3 个项目的门槛过高

「对外素材不用真实数据」这条可能只在当前项目出现过。其余项目没有这条记忆，于是它永远凑不齐 3 个项目，永远无法晋升——**哪怕它明显是正确的通用原则**。

三种修法：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 降门槛 | 2 个项目命中即提议 | 误报率上升 |
| 加旁路 | 单项目高置信 + 用户在面板手动「提升为全局」 | 需要 UI，但完全可控 |
| 加权 | 按锚点数量计分，2 个项目 × 3 锚点 也能达标 | 规则复杂，难解释 |

建议同时采用**方案 1（门槛降为 2）与方案 2（手动提升旁路）**：自动路径保守，人工路径兜底。纯自动永远会有漏网，但用户始终有决定权。

## 对实现的启示

1. 蒸馏提示词要显式禁止三类内容：项目载体、单锚点结论、常识性套话。这三类占了淘汰量的绝大部分。
2. 候选原则的存储必须包含锚点 id（项目内），否则无从复核，也无法计算「这条原则有多少证据」。
3. `feedback` 类应给更高权重——本次 4 条合格产物里，3 条的主要锚点来自 feedback/decision，而不是 convention。
