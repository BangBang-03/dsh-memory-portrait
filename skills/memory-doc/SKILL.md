# 项目记忆文件的标准化更新

## 适用场景

- 用户说「更新 MEMORY.md」「补一条项目约定」「把这个记进项目」「换机器后把记忆整理一下」。
- 要在没有装 dsh-memory 的机器上交接项目，需要一份能独立读懂的上下文。
- 整理已有的 `.dsh-memory/MEMORY.md`：去重、补理由、修结构。

## 第一步：判断插件在不在

这一步走错，后面的工作会全部白做。

| 情况 | 怎么做 |
| --- | --- |
| **装了 dsh-memory** | **不要直接编辑 `MEMORY.md`**。每次写入都会按条目库整份重渲染，手改会在下一次写入时被覆盖。改用 `memory` 工具（`save` / `update` / `forget`）或设置面板写条目，镜像自动跟随。 |
| **没装 dsh-memory** | 直接编辑 `MEMORY.md`。此时它是这个项目唯一的记忆载体，没有后备数据源。 |

判断方式：看 `<工作区>/.dsh-memory/` 里有没有 `memory-snapshot.json`。有 = 插件在维护（它和 MEMORY.md 同时生成、同时撤回）；只有 `MEMORY.md` = 离线状态。

## 结构（顺序固定，不要重排）

```markdown
# 项目记忆 — <项目名>

> 来源声明：谁在维护、能不能手改、改了会怎样
> 完整条目指针（装了插件时指向 memory-snapshot.json）
> 工作区 ｜ 条数 ｜ 更新日期

## 项目概况        ← 这个项目是什么、为谁解决什么问题
## 当前关注        ← 现在在做哪几件事、卡在哪
## 不能碰的规矩    ← 绝对禁令，逐字，不许摘要或软化
## 置顶            ← 跨类别的高优先级条目
## 约定（convention）等分类
```

为什么画像段要排在条目之前：离线读者第一个问题是「这是什么项目」，不是「第三条约定写了什么」。

### 条目格式

```markdown
- **标题** — `tag` · 2026-11-05
  正文。一句话说清这条约定是什么。
  为什么：没有理由的约定，半年后没人敢删。
  ↩ 替代了「旧标题」
  ⇔ 关联：相关条目标题
```

- 标题：名词短语，能被 grep 命中。不要写「关于那个问题的讨论」。
- 正文：**不截断、不摘要**。这份文件是唯一载体，压缩等于丢信息。
- `为什么`：写触发它的具体事件或后果，不写「这样更好」。
- 版本链：新条替代旧条时，两处都要标注，不要直接删掉旧的。

## 写作规范

1. **一条一件事**。两件事写成两条，别合并成一段——合并后无法单独废弃。
2. **结论 + 理由**。「必须用 pnpm」是结论，「npm 装出来缺 peer 依赖，上次因此白跑两小时」是理由。
3. **绝对表述写约束**（必须 / 不要 / 永远），**条件表述写事实**（在 X 下成立 / 只在 Y 时）。
4. **用绝对日期**，不写「上周」「昨天」「本次」。日期只取条目创建时间，不要用最后修改时间——那会让同一份文件每次打开都不一样。
5. **不写密钥、token、内网地址、他人隐私**。写进项目目录意味着可能被提交进 git，而 git 历史不可撤销。
6. **决策类写三段**：选了什么 / 放弃了什么 / 什么条件下应该推翻。

## 校验清单

改完逐条过一遍，任何一条不过就不要提交：

- [ ] 红线区**逐字未改**。禁令被「优化」措辞是最危险的失败模式。
- [ ] 没有草稿内容混入。待审的、没确认的结论不该出现在这里。
- [ ] 同一主题没有两条互相矛盾的条目。有冲突就合并，或标 `supersedes` 保留时间线。
- [ ] 每条都有理由。只有结论的条目，后来人无法判断它是否还成立。
- [ ] 没有相对时间表述（「最近」「目前」「本次」）。
- [ ] 装了插件的情况下，确认这次改动是走条目库完成的，不是手改镜像。

## 常见错误

| 错误 | 后果 |
| --- | --- |
| 装了插件还手改 `MEMORY.md` | 下次写入被整份覆盖，改动无声消失 |
| 为了「精简」截断正文 | 唯一的离线载体丢信息，换机器后查不到细节 |
| 把 `MEMORY.md` 当待办清单 | 任务有生命周期，记忆只放不会过期的结论；待办走 journal 或任务系统 |
| 整段对话粘进来 | 噪声压倒信号，读者要自己提炼——那还不如不写 |
| 按日期拆成多个文件 | 本项目刻意只用一份文件承载全部；日期只作为条目元数据，不作为分节依据 |
